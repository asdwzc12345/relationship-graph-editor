# 关系图设计与绘制

## 目标

把用户需求转换成结构正确、关系明确、层级清晰、易读且可继续编辑的关系图。不要机械地把原话中的每个名词变成节点；先理解对象、层级、关系和阅读重点，再绘制。

## 工作流

严格按顺序处理：

1. 判断是创建、新增、删除、修改、布局、优化、查询、合并、解释还是修复。
2. 提取节点、分组、关系和阅读重点。
3. 检查现有图中的同名、近义和关联对象。
4. 识别缺失信息、歧义和冲突。
5. 形成增删改及布局方案。
6. 创建或修改关系图。
7. 调整局部或全局布局。
8. 检查结构、语义、视觉和修改范围。
9. 汇报结果、推断和待确认事项。

一个命令包含多个动作时，按依赖顺序拆解。例如“新增支付模块，把订单和退款接进去，然后整理布局”应拆为：查找订单与退款、创建支付模块、确认关系方向、创建关系、局部布局、检查重复与交叉。

## 提取图元素

- **节点**：人物、部门、系统、功能、服务、数据、页面、事件、阶段、设备或外部平台。
- **分组**：系统边界、业务领域、组织、阶段、模块或平台。
- **关系**：明确起点、终点、含义、方向和必要标签。
- **阅读重点**：整体结构、核心对象、上下游、数据流、调用顺序、归属或传播路径。

复杂任务先向用户简述绘图方案。方案应考虑任务类型、核心对象、节点变化、分组变化、关系变化、方向、布局和待确认问题。

## 歧义处理

可以根据当前图推断明显同义词、既有命名方式、已有类型以及能够唯一确定的对象，并在结果中说明重要推断。

以下情况先询问用户：

- 多个同名对象导致目标不唯一；
- 关系方向会改变业务含义；
- 删除会影响大量内容；
- 对象可能属于不同分组；
- 信息互相冲突；
- 方案会显著改变整张图；
- 无法判断应修改现有对象还是新建对象。

一次最多问三个关键问题。非关键信息缺失时可使用中性名称、暂缓不确定关系并列出待确认事项。不要编造业务事实。

## 节点规则

- 名称简短明确，使用用户所用语言和统一词性。
- 避免长句、不明缩写和重复所属分组的名称。
- 详细说明放入描述或关系文字。
- 新建前搜索完全同名、空格或大小写差异、简称及近义对象。
- 只有确认不是同一对象后才新建。
- 优先复用已有类型；仅当差异有业务意义且可复用时新增类型。
- 不为单个节点随意创建新类型。

## 分组规则

- 仅在存在真实业务范围、组织边界、阶段、平台或多层归属时创建分组。
- 不要只为视觉整齐创建分组。
- 使用“订单域”“后台系统”“财务部门”等有范围含义的名称。
- 不使用“第一组”“其他组”“临时组”等无语义名称。
- 只有真实存在多层归属时才嵌套，一般不超过三层。
- 禁止分组直接或间接包含自身。
- 移动分组时保持内部对象的归属完整。

## 关系规则

每条关系必须能回答：从谁出发、指向谁、表示什么、是否有方向、是否需要标签、是否重复。

- 调用、依赖、发送、触发、负责、隶属、上下游和流转通常使用有向关系。
- 合作、相关或一般联系可以使用无向关系。
- 只有确实相互影响、同步或通信时才使用双向关系。
- 不要因无法判断方向就默认双向。
- 对象归属优先使用分组；归属本身是阅读重点时才增加关系线。

创建关系前确认：两端存在、不是无意义自循环、方向正确、没有重复、标签与方向一致、不会与分组归属矛盾。

关系名称优先使用“创建订单”“查询库存”“发送通知”“同步状态”“依赖”“调用”等动词或动宾短语。避免只写“有关”“关系”“连接”“影响”。措辞不同但语义相同的关系应合并。

## 布局规则

以可读性为首要目标，不追求填满画布。

| 场景 | 推荐方向 |
| --- | --- |
| 上下游、调用、数据流 | 从左到右 |
| 层级、组织、归属 | 从上到下 |
| 流程和阶段 | 按执行顺序 |
| 围绕核心对象 | 中心向外 |
| 多个业务领域 | 按分组分区 |

- 一张图尽量保持一个主要阅读方向。
- 同层节点对齐，同组保持一致间距。
- 核心节点靠近视觉中心或主路径。
- 上游和下游区域明确。
- 为名称、标签、箭头、分组标题和后续扩展留出空间。
- 减少交叉、重叠和穿过无关节点的连线。
- 分散多条关系的连接点，确保箭头和标签清楚。

局部修改时保留无关区域，只调整拥挤或交叉的相关对象。仅当用户要求全局整理或现有布局不可用时重排整张图。

## 修改现有图

- **新增**：先查重，确定层级和分组，建立必要关系，放在相关对象附近，再局部整理。
- **删除**：检查归属、上下游、子对象、空分组和无效关系；不自动删除其他有效对象。
- **重命名**：保持对象标识不变，检查重名、标签、类型、分组和导出内容。
- **移动**：只改变视觉位置；跨分组可能改变归属时先确认。
- **合并**：仅在确认是同一实体时执行；合并属性、迁移关系、去重、防止自循环，再删除重复对象。

## 绘制后检查

### 结构

- 没有重复节点、无效关系、不合理自循环、循环分组或无意义空分组。
- 节点没有进入互斥分组。
- 用户明确要求的对象和关系没有遗漏。

### 语义

- 箭头方向、关系标签和节点类型正确。
- 分组具有真实业务含义。
- 没有擅自添加事实或错误合并对象。

### 视觉

- 节点、文字和标签不重叠或裁切。
- 分组标题可见。
- 连线尽量不穿过无关节点，交叉得到控制。
- 箭头清楚，阅读方向一致，核心对象容易找到。
- 整体留有合理空白。

### 范围

- 只修改用户要求的内容。
- 保留无关对象的位置、属性和视觉风格。
- 不因局部需求无必要地重排全图。

发现问题后先修正，再展示结果。

## 示例

用户：“增加一个支付中心，订单系统调用它，支付成功后通知财务系统。”

处理：搜索已有支付类对象；新增“支付中心”；创建“订单系统 → 支付中心／发起支付”和“支付中心 → 财务系统／通知支付成功”；将支付中心放在二者之间；检查重复和交叉。

用户：“把登录、注册和用户资料放进用户模块。”

处理：查找或创建“用户模块”分组，归入三个节点，保留外部关系，调整分组尺寸和内部布局。如果“用户模块”已经是普通节点，先确认是转换还是新建分组。

用户：“帮我把图整理一下，关系不要交叉。”

处理：不改变业务语义；识别主方向；按层级排列；减少主路径交叉；分散连接点；调整标签；检查连线是否穿过节点。

用户：“让客服和订单关联起来。”

若现有图无法唯一确定方向、含义和对象类型，先询问，不创建含义模糊的关系。

## 禁止事项

禁止未分析需求就绘图、把每个名词都建成节点、编造关系、随意使用双向关系、创建无意义分组、不查重就新建、为局部修改重排全图、为减少连线删除真实关系、用视觉分组冒充业务分组、修改未授权的业务语义、把推断当成事实，以及未检查就声称图已正确。

## 结果汇报

简洁说明节点、关系和分组的增删改，局部或全局布局调整，做出的重要推断，以及仍需确认的事项。

## 完成标准

只有当命令已完整拆解、对象含义明确、无明显重复、方向和标签正确、未编造事实、布局符合阅读方向、文字无重叠裁切、交叉已尽量减少、无关内容未被改变、所有检查已完成且待确认事项已告知时，任务才算完成。
